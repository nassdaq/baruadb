Inside Barua Functions

What happens when you hand us a repository, what runs when a call arrives, what we keep and what we throw away. Each part, drawn.

From a repository to a URL

You name a repository. We fetch it, compile it, and keep one file: a WebAssembly module. That file answers at a URL that belongs to your organisation.

What your repository needs

Very little. A program that reads its input on stdin and prints its answer on stdout, with the one file that tells us which language it is. Everything else in the repository is ignored.

The smallest working function - Rust

# Cargo.toml
[package]
name = "greet"
version = "0.1.0"
edition = "2021"

// src/main.rs
use std::io::{self, Read, Write};

fn main() {
    let mut input = String::new();
    io::stdin().read_to_string(&mut input).ok();
    let name = input.trim();
    write!(io::stdout(), "{{\"hello\":\"{}\"}}", if name.is_empty() { "world" } else { name }).ok();
}

The same in Go

// go.mod
module greet

go 1.22

// main.go
package main

import ("fmt"; "io"; "os"; "strings")

func main() {
    in, _ := io.ReadAll(os.Stdin)
    name := strings.TrimSpace(string(in))
    if name == "" { name = "world" }
    fmt.Printf("{\"hello\":%q}", name)
}

A crate that is also a server

One repository can be both: the HTTP server on a real machine, and a function here. Keep the server's dependencies out of the function's build with a target condition, and pick the entry point by target. This is how pasaka-api is laid out.

# Cargo.toml
[dependencies]
serde_json = "1"                       # compiled everywhere

[target.'cfg(not(target_os = "wasi"))'.dependencies]
axum = "0.8"                           # only on a real OS
tokio = { version = "1", features = ["full"] }
sqlx = { version = "0.8", features = ["postgres", "runtime-tokio-rustls"] }

// src/main.rs
#[cfg(target_os = "wasi")]
fn main() { function::run() }          // stdin → stdout

#[cfg(not(target_os = "wasi"))]
#[tokio::main]
async fn main() { server::run().await } // the HTTP server

Rules of thumb: read all of stdin, print the answer, exit 0 - a non-zero exit is reported to the caller as a failure. Nothing that opens a socket or a file will work inside the function; a database goes through DATABASE_URL and the host.

What happens to your code

The build runs in a scratch folder that exists only for that build. When it ends, success or failure, the source and every build artifact are deleted. What survives is the module, the compiler's log, the commit hash and the address of the repository.

A call, step by step

A request reaches barua.tz, which checks your API key and asks the runtime on the Tanzania box. The runtime gives the call a brand-new sandbox: your body on stdin, your environment variables, and nothing else of the machine. Whatever the function prints is the response.

Awake and asleep

A function is a server that costs nothing while nobody calls it. The first call starts a warm instance; calls keep it warm; ten minutes of silence retire it. The next call wakes it with a cold start of a few milliseconds, which the page counts.

Your database, through the host

The sandbox has no network, so the function asks the host. Set DATABASE_URL in its environment; your code calls barua_fn::query; the host runs the statement over a connection it keeps warm and hands the rows back into the sandbox as JSON. A Barua database in the same region shares the box, so a query is a few milliseconds.

The API tab

A barua.json next to your code lists what the function can do: a name, a line, the body to send. We keep it with the module, and the API tab turns each entry into the exact request to copy, with your key filled in, and a Try button.

What we record

Enough to run the thing and show you what it did, and no more.

What deleting removes

Delete a function and the runtime removes its module, settings, environment, call log, events and usage at once; its records in barua.tz go with it. Its URL stops answering immediately. Your repository is untouched, as it always was.
