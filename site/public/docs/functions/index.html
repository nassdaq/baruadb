Barua Functions

Your own code — in Rust, Go, or anything that compiles to WebAssembly — run sandboxed, next to your data, and asleep when nobody is calling it. One call to deploy a function, one call to run it, billed by the millisecond it actually spends working.

Overview

Sometimes the work does not belong in your app and does not belong in the database either: validate a webhook, score a row, reshape a payload, do a burst of real arithmetic. Renting a server for that means paying for a machine that sits idle between calls. A function is the opposite — it exists only while it runs.

The unit is a WebAssembly instance, not a container: a few kilobytes, started in well under a millisecond, thousands to a host, and nothing at all while idle. A container cold-starts in one to three seconds; a Rust function here cold-starts in about three milliseconds. That is the whole reason this tier can be cheap.

The contract is one sentence: a function reads its input on stdin and writes its result on stdout. Every language's standard library already speaks it, so there is no framework to learn and nothing to import.

You doBarua does
PUT a compiled .wasm modulestores it, ready to run — deployed
POST an input to itruns it in a fresh sandbox, returns what it wrote to stdout
nothing, between callsnothing — the function does not exist until the next request, and costs nothing

Quickstart

  1. Switch it on. Functions is enabled per database, like Tasks. Turn it on for a database and you get an endpoint and a key — save the key as BARUA_FN_KEY in your environment. (Early access: ask us to switch it on from the console.)
  2. Write and compile. A function reads stdin and writes stdout. In Rust, build it for the WebAssembly target: 
    rustup target add wasm32-wasip1
cargo build --release --target wasm32-wasip1
# → target/wasm32-wasip1/release/your-fn.wasm  (tens of kilobytes)
  3. Deploy. PUT the module under a name you choose: 
    curl -X PUT -H "Authorization: Bearer $BARUA_FN_KEY" \
     --data-binary @your-fn.wasm \
     https://fn.pg.barua.app/fn/score
  4. Run. POST the input; the body back is exactly what your function wrote: 
    curl -X POST -H "Authorization: Bearer $BARUA_FN_KEY" \
     --data '42' https://fn.pg.barua.app/fn/score
# {"fib":267914296}   ·   see the x-fn-ms header for how long it took

Write a function

Read stdin, write stdout. That is the entire interface — the same one cat uses. Here is a real function (a little arithmetic) in two languages; both run through the identical sandbox.

Rust

use std::io::{self, Read, Write};

fn main() {
    let mut s = String::new();
    io::stdin().read_to_string(&mut s).ok();
    let n: u64 = s.trim().parse().unwrap_or(10);
    write!(io::stdout(), "{{\"fib\":{}}}", fib(n)).ok();
}

Go — GOOS=wasip1 GOARCH=wasm go build -o fn.wasm .

func main() {
    data, _ := io.ReadAll(os.Stdin)
    n, _ := strconv.ParseUint(strings.TrimSpace(string(data)), 10, 64)
    os.Stdout.WriteString(fmt.Sprintf("{\"fib\":%d}", fib(n)))
}

Your input arrives on stdin as whatever you POST — a number, a line of text, a JSON document. Parse it, do the work, print the answer. Anything written to stderr comes back to you on failure, so it is the place for a log line.

Deploy

A deploy is one request: PUT /fn/:id with the compiled module as the body. The name :id is yours to pick ([a-z0-9][a-z0-9_-], up to 64 characters); PUT again to the same name to replace it, and the next call runs the new code.

curl -X PUT -H "Authorization: Bearer $BARUA_FN_KEY" \
     --data-binary @fn.wasm  https://fn.pg.barua.app/fn/score
# {"id":"score","size":38180,"deployed":true}

Invoke

POST /fn/:id with your input as the body. The response body is your function's stdout, verbatim, with two headers worth reading:

  • x-fn-ms — the wall-clock milliseconds the run took, the number you are billed on.
  • x-fn-exit — the exit code; 0 is success.
curl -X POST -H "Authorization: Bearer $BARUA_FN_KEY" \
     --data '45' https://fn.pg.barua.app/fn/score
# {"fib":1134903170}

Every call gets a fresh instance: fresh memory, nothing carried over from the last call or from anyone else's. A function cannot see another's data because, by the time the next one runs, the last one no longer exists.

Languages

Anything that compiles to wasm32-wasip1 runs unchanged. The two ends of the trade-off:

Rust

The dense end. A Rust function is tens of kilobytes because it bundles nothing but your code, and it starts in milliseconds. Best for the hot path — the function you call on every request.

rustup target add wasm32-wasip1
cargo build --release --target wasm32-wasip1

Go

The familiar end. Go 1.25's own compiler targets WebAssembly, no TinyGo required. A Go module is larger (it ships its runtime and garbage collector) and starts a little slower, which is the honest cost of its convenience.

GOOS=wasip1 GOARCH=wasm go build -o fn.wasm .

Any WASM language

Zig, C, AssemblyScript, TinyGo — if the toolchain can emit wasm32-wasip1 and the program reads stdin and writes stdout, it runs here with no change on our side. The sandbox does not know or care which language wrote the module.

How it is sandboxed

A function can touch its input and its output, and nothing else. It has no network, no filesystem, no view of the host or of any other function — a WebAssembly module only reaches what it is explicitly handed, and a function is handed stdin and stdout.

  • Fresh per call. Each invocation is a new instance with its own memory; state never leaks from one run to the next.
  • Isolated. A function runs on its own thread with its own memory, so a crash or a hang takes down that one call, never the host or a neighbour.
  • Bounded. A function that runs past its time limit is stopped and the call returns an error — one runaway loop cannot hold the service.

Speed, measured

Measured on one thread, deploying and calling over the internet — not a lab figure:

LanguageModuleCold runWarm runThroughput
Rust38 KB3.2 ms0.245 ms1,545 / s
Go2.1 MB11.5 ms1.5 ms509 / s

Cold run is a fresh sandbox instantiated and executed once — what a scale-to-zero call costs. For comparison a container's cold start is one to three seconds. The size gap is the whole story about efficient languages: Rust bundles nothing, Go bundles its runtime, so Rust starts about six times faster and packs about three times denser.

API reference

The endpoint is the one the console gives you (https://fn.pg.barua.app in early access). Every /fn route takes Authorization: Bearer <your key>.

Method and pathBodyDoes
PUT /fn/:idthe .wasm moduledeploy or replace it → 201
POST /fn/:idthe input, any bytesrun it; returns stdout, with x-fn-ms and x-fn-exit
GET /fn/:id—whether it is deployed and warm

A run that fails answers 500 with { "error": … } and whatever the function wrote to stderr; a run that exceeds the time limit answers 504; a call without a valid key answers 401.

Limits

  • Module up to 32 MB; input up to 256 KB.
  • A call has 5 seconds to finish; past that it is stopped and returns 504.
  • A function sees no network and no filesystem in early access — input in, output out.
  • The function name is [a-z0-9][a-z0-9_-], up to 64 characters.

Troubleshooting

401 on every call. The Authorization: Bearer header is missing or the key is wrong. Deploy and invoke both need it; only health does not.

400 not a WebAssembly module. The body you PUT was not a .wasm file. Check you sent the compiled artifact (target/wasm32-wasip1/release/*.wasm, or the -o fn.wasm from Go) with --data-binary, not --data, which mangles bytes.

504, timed out. The run took longer than five seconds. For heavy work, split it — or reach for the container tier, which exists for jobs a millisecond-billed function should not hold.

Big module, slow start. Usually a Go build. If the function is on your hot path, the same logic in Rust or Zig is a fraction of the size and starts in milliseconds.
